# 2026-11-06 요청 성공·실패 조건과 관찰 공백 조사

## 요구사항·조사 결과
사용자는 조용한 운행도 약속을 어기면 실패가 아니냐고 지적하고, 요청별 실제 성공/실패 조건과 실패가 없는 이유를 정리해 달라고 요청했다. 직전의 ‘실패 판정 없음’은 설계상 실패가 불필요하다는 뜻이 아니라 현행 관찰기/행동 기능이 없다는 뜻임을 정정했다.

`PassengerRequestObservation.Finish`, `PassengerRequest`, `PassengerRequestUI`, `PassengerJobs`의 실제 하차 경로, 활동/상황 및 선택지 코어·카탈로그, 승객/대화 기획을 대조했다. [17종 실제 판정표](../content-tuning-request-outcomes.md)에 성공·실패·판정 불가·미응답·운송 중단을 구분했다.

- Quiet는 수락 시 후속 상황 대화와 취객 일반 수다를 자동 억제하지만, 나중의 약속 위반 행동을 추적해 실패시키지는 않는다. 정상 도착 시 성공 처리다. 예약 요청·필수 안전/승하차 안내는 별도다.
- Comfort는 수락 후 급가속/급제동/충돌 사건 증가, OnTime은 요청 시작 후 확정 법규 위반에 실제 실패가 발생한다. OnTime 지각만 있고 위반이 없으면 판정 불가이며 지각 운임 처리는 별개다.
- 큰길/짧은 길은 수치 목표가 있지만 미달 사유를 구분하지 못해 판정 불가로 처리한다. 경로 추천의 선호 변경도 판정 불가다.
- 안전 하차/목적지 변경/경유 용무는 실패 분기가 있으나 일반 하차 절차가 조건 충족을 강제해 실패 평가에 도달하기 어렵다. 이는 코드 경로 추론이며 새 수동 플레이 입증이 아니다.
- 공감/면접/지역/운임은 응답 완료, 음악은 텍스트만, ETA는 예상 안내다. 모두 ‘실패가 절대 불필요’로 동일시하지 않는다. 분실물은 하차 후 별도 사건이며 불법 요구 거절 뒤 실제 위반은 요청 판정 불가+독립 법규/M 기록이다.
- 관리창은 결과에 붙는 효과값을 편집하며 성공/실패 조건 자체는 코드에 고정되어 있다. 새로운 Quiet 실패 점수 칸만 추가해도 위반 관찰이 생기지 않는다.

## 후속 논의: 승객 요청과 차내 장치 실제 조작
- PassengerBehavior의 온도 선택이 TemperatureSetting을 직접 바꾸고 유지 시간을 평가하는 구조, PassengerRequest의 Music이 응대만 제공하는 구조를 확인했다.
- 제안: 승객 요청 → 수락/보류 → 공통 차내 제어 UI로 실제 장치 변경 → 일정 시간 상태 관찰 → 승객 반응. 차량 상태와 승객별 요청 평가를 분리하고 답변만으로 장치를 바꾸거나 점수를 주지 않는다.
- 간단한 제어 패널과 운전석 장치 표현을 연결하는 방식을 우선 제안한다. 온도·음악·창문의 최소 단계, 기존 온도 보상과 중복 방지, 안전한 조작 기회·짧은 운송의 판정불가, 저장 및 PvP 호스트 판정을 설계에서 다룬다.
- 사용자 설계 논의이며 기존 보류 해제나 구현 승인을 가정하지 않는다. 새 기획 확정·코드/빌드 변경·실행 검증 없음.

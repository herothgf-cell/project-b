# 선택지 효과 구조 조사 — 현재 구현과 요청한 구조의 차이

**역사 자료 — 독립 선택지 효과 구현 전 조사.** 아래의 현재/미구현 표현은 조사 당시 상태이며 지금의 기능 제한이 아니다. 승인된 구현 기준은 [선택지별 단계 효과](../superpowers/specs/2026-11-06-independent-choice-effects.md), 사용 방법은 [관리 도구 안내](../content-tuning-tool-guide.md)를 따른다. 조사 당시에는 밸런스나 효과를 변경하지 않았다.

## 현재 확인된 동작

| 항목 | 실제 동작 | 편집 한계 |
|---|---|---|
| 예상 도착 안내 | 빠름/내비/여유는 예상 시간 표현만 달라진다. 요청 점수는0 | success/failure/unanswered 전부 읽기 전용0. 독립 점수 키가 없다 |
| 공감: 이야기 듣기 | 수락 직후 점수0, 하차 때 요청 이행+5 | 공감 요청 공통 success를 사용 |
| 공감: 조용히 배려 | 수락 직후 점수0, 하차 때 동일+5. 후속 제한 추가 | 다른 방식의 정상 응대로 구현. 거절이 아니다 |
| 공감: 미이행−5 표시 | 정상 운행에서 실패로 판정하는 경로 없음 | 카탈로그의 미사용 참고값이며 읽기 전용 |
| 공감: 안전상 보류 | 요청 수락하지 않음,0 | 별도 Defer 답변 |
| 공감: 미응답 | 안전한 응답 기회 뒤 끝까지 미응답이면 하차 때−5 | failure와 별도 unanswered 설정 |
| 멀미·편안한 운행 수락 | 수락 뒤 급가감속 M 감점 기본2→4, 종료 때 이행+8/미이행−10 | 특정 요청 전용 분기. 임의 선택지의 일반 효과 목록이 아니다 |
| 음식 허용 | 음식 유형의 허용 선택에서 승차 후+5, 실제 섭취/흘림 때 청결 감소 | 별도 승객 유형 로직. 일반 대화 선택지 효과 시스템이 아니다 |
| 피로 | 경과 시간·허기·휴식 등으로 계산 | 선택지별 즉시 피로 증감·피로 증가율·종료 효과 없음. 시간 지연은 간접 영향 |

`PassengerRequest`에는 선택한 답변이 저장되지만, 점수 계산은 `Delta(Kind, success)`다. 답변 종류는 점수 인자로 사용하지 않는다. 따라서 현재 기본 구조는 **요청 종류별 이행/미이행/미응답 공통 점수 + 일부 전용 행동**이다.

카탈로그가 readonly로 표시한 ETA 항목은 `ContentTuning.ConfigureCatalog`에서 활성 편집 목록에 넣지 않는다. UI 잠금만 푸는 것으로는 부족하다. 한 개의 ETA success만 열어도 세 답변이 같은 값을 공유하므로 사용자가 요청한 독립 설정과 다르다. 임의의 per-reply 점수 키는 실제 프로필 검증이 거부한다.

공감의 ‘조용히 가실까요?’는 코드에서 정상 수락(`Alternative`)과 조용한 배려로 처리한다. 듣기와 조용한 배려에 각각 다른 점수를 주고 싶다면 답변별 효과 데이터를 분리해야 한다. ‘이야기를 듣지 않았으니 실패’라고 자동 판단하는 규칙은 없다.

## 후속 제한의 실제 범위

조용한 운행 수락 또는 공감/면접의 조용한 배려는 해당 운송의 신호 대기·흔들림 같은 **새 추가 상황 대화와 취객 일반 수다**를 제한한다. 확률을 조금 낮추는 값이 아니다. 별도로 배정된 다음 요청과 필수 안전/승하차 안내를 모두 취소하는 기능도 아니다. 승객 유형의 Quiet와 상황 답변의 Quiet는 적용 범위가 서로 다르다.

## 요청한 목표 구조 — 미구현 제안

승객 요청 안의 **각 선택지**가 아래 효과를 독립적으로 소유한다.

| 단계 | 편집할 내용 | 적용 예 |
|---|---|---|
| 선택 직후 | 만족도 증감, 피로 증감, 후속 대화 제한 | 이야기 듣기 만족도+5 / 조용한 배려0 등을 각각 설정 |
| 운행 중 | 조건별 추가 감점, 만족도 변화율, 피로 증가율 변경과 유지 기간 | 수락 이후 불필요한 급제동에 M 추가 감점, 해당 승객 운송 동안 피로 증가율 변경 |
| 운송 종료 | 이행 조건, 이행·미이행 결과, 판정 불가 결과 | 부드러운 운행을 지켰을 때 추가 보상, 실패 시 별도 감점 |
| 답하지 않음 | 응답 기회 조건과 독립 결과 | 선택지를 누르지 않은 상황은 선택지의 실패와 분리 |

위 숫자는 구조 설명 예시이며 새 밸런스로 적용하지 않았다. **증감량0/추가율0은 효과 없음**으로 정의한다. ‘피로 증가율 변경0%’는 기존 증가율 유지이며, 피로 자체를0으로 만들지 않는다. 점수는 승객 만족도 S와 운전 만족도 M을 구분한다.

즉시 효과와 종료 보상을 동시에 설정하면 둘 다 적용될 수 있으므로 UI에 시점과 합계 기여를 표시해야 한다. 한 효과를 시점마다 재지급하면 안 된다. 현재 요청 합계 상한±10에 어떤 기여를 포함할지, 운행 중 변경의 유지 기간/중도 종료 처리를 데이터로 명확히 정해야 한다. 임의 코드 실행 대신 지원되는 효과와 관찰 조건을 선택하는 방식이 적절하다.

게임 코어에는 선택지별 효과 데이터·누적 기여·적용 완료 기록·운행 중 활성 상태가 필요하다. 이어하기/사고 취소/도착 시 중복 적용을 막고, 프로필 검증/저장 snapshot/호스트 LAN/봇/미리보기를 함께 갱신해야 한다. 기존 프로필은 현재 동작을 유지하도록 이관한다. 표시 편집만으로 완료되는 변경이 아니다.

## 근거와 검증

- `unity/EungyeTaxi/Assets/Scripts/PassengerRequest.cs`: 수락은 점수0, 종료 점수는 Kind 기준, 미응답 별도, 선택 답변 저장.
- `PassengerRequestObservation.cs`: 공감 두 응대의 수락/종료 경로, ETA 안내, 멀미 강화 M.
- `PassengerBehavior.cs`, `PassengerJobs.cs`: 음식 유형 효과와 최종 만족도 기여.
- `ContentTuning.cs`, `config/content/catalog.json`: readonly 제외·임의 키 거부.
- `DriverCondition.cs`, `EconomyLedger.cs`: 시간/허기에 따른 피로 증가. 요청 답변 인자 없음.
- 실제 순수 C# 요청 클래스와 설정 코덱을 분리 컴파일한 `tools/test_choice_structure.ps1`: **16검사 통과**. MonoBehaviour 전체 운행이나 Player 주행 검사는 아니다.

## 이번에 반영한 관리창 정리

‘운송 종료 평가’/‘답하지 않았을 때’/‘모든 요청에 적용되는 공통 설정’을 분리했다. 요청 평가 점수의 편집칸은 한 곳에만 두고 선택지에서는 미리보기/평가 이동을 제공한다. 사용하지 않는 실패값은 실제 결과 미리보기에서 제외하고 ‘현재 미사용(참고값)’으로 표시한다. 각 항목에 적용 시점과 영향 대상을 붙였다. 이는 **현재 동작을 명확히 설명하는 UI**이며 위 독립 선택지 효과 엔진의 구현을 뜻하지 않는다.
